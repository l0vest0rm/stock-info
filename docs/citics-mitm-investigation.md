# 中信证券网上交易：本机接口调查（未完成的协议验证）

2026-11-10，目标是本机安装的 `com.citics.mac.tdx`。本文件仅记录可复核的安装包证据和拦截结果；**没有可用的下单接口，也没有发出委托**。

## 已确认的边界

- 安装包 `Contents/Resources/home.zip` 内的 `home/jycfg/eTrade.xml` 区分普通交易（`HostType=0`）和信用交易（`HostType=1`）。二者的会话/账户上下文不能混用。
- `home/syscfg/UIConfigTrade.xml` 声明普通买入、卖出及信用担保品买入、担保品卖出、融资买入、融券卖出等不同 UI 操作。`home/webApp/app/mainhtml/trade.html` 与 `trade_xy.html` 含相应的功能标识；担保品买卖沿用 `TM_MRWT`/`TM_MCWT` 的页面标识，因此这些字符串**不是**可独立调用的网络下单 API。
- `home/webApp/tlibs/pc-js-api.js` 声明通过 `window.TDXQuery` 发送 `{Method, FuncName, Param}` 的页面到原生客户端桥接调用；可见 `ASK_HQData`（即时行情）和 `ASK_ZSTData`（分时）等功能名。这不能证明原生客户端的网络协议、参数格式或服务端响应。
- 运行中的原生程序有连接至 `7708`；安装包的 `home/syscfg/taapi.xml` 明确将此端口列为普通交易主站（集群 `9991`），而 `7709` 属于行情主站。已存在的 TCP 会话不因随后启动本机 mitmproxy 而自动被代理。第一轮尝试了仅针对该进程的本地代理模式，未捕获到新增的消息，随后停止。
- 电脑控制工具随后返回 `sensitive_ui`，不能观察或操作当前交易界面；不能绕过保护去点击下单或重启/终止当前会话以强制重连。

## 第二轮监听（300308、588000）

用户选择这两个证券后，进程仍复用原有到 `202.108.253.147:7708` 的**交易** TCP 会话，定向本地代理截至本轮检查未收到新消息。直接通过 `tcpdump` 捕获 `en0` 因 BPF 设备权限被拒绝；不能将零条代理记录解读为页面没有发送请求。等待用户只重连行情主站后再核验新连接及两个代码对应的消息。不要捕获交易账户端口或保存委托/鉴权正文。

用户随后重新启动 App，进程 PID 由 `61599` 变为 `63374`。先前代理按旧 PID 过滤，未覆盖新启动；已改用应用进程名称过滤，仍须验证实际是否截获新建的行情连接，而不是仅凭代理启动成功推断抓包成功。

### 重连后取得的行情证据

应用按名称过滤的 mitmproxy 在行情主站重连后实际捕获到 `7709` 的双向 TCP 消息；含 `300308` 和 `588000` 的客户端行情消息分别出现 16 次和 35 次。首次过滤误将交易端口 `7708` 当作行情端口；发现安装包内集群映射后已立即停止代理、从本机捕获文件移除全部 45 条该端口记录，并将过滤器改为仅保留 `7709`。从未提交或上传这些记录。原始行情数据仅在本机忽略目录 `data/mitm-investigation/quote-messages.jsonl`，**不得提交、上传或当作交易样本**。

两种证券的请求均出现 `0x1214`（按捕获帧字节 `12 14` 的表示），对应的响应长 332 字节，包含证券代码；例子里从偏移 232 开始，交错排列十组 10 字节记录（小端 `f32` 价格、`u32` 数量、2 字节未明字段）。`300308` 的首组价格/数量是 `471.00/809`，随后可见 `471.01/5`、`470.99/4` 等；`588000` 的首组是 `1.337/166989`，随后 `1.338/125543`、`1.336/75128` 等。这强烈符合最新价与买卖五档，但**买卖方向、数量单位和字段含义仍须同一时刻对照 App 页面验证**；TCP 消息边界也不等于完整协议帧边界。

保留的证据只包含行情端口与股票页面切换，**未观察任何下单提交、预校验或委托回执**。买入/卖出真实接口的请求字段、账户绑定和可重试语义仍不能从这份行情流量推断。

尝试以 REA 静态搜索原生可执行文件中的交易调用时，常规 Ghidra 未配置、Hopper 不存在；实验性 `ghidra-rs` 可以检索到 `GetServerTradeCCf2` 等字符串，但未找到直接引用或可定位的同名过程，不能从字符串推导下单格式。静态页面上的 `TM_MRWT` 等入口不能代替交易报文证据。仅用手动切换股票可以确认行情查询，不能推导提交委托的线协议。当前本机交易界面被桌面控制工具的 `sensitive_ui` 保护拒绝，不能通过该工具代替用户点击或输入。

## 独立 crate 进展

`crates/citics-api` 已将抓包确认的 `0x1214` 五档行情请求和响应解析为隔离的 Rust API（包括最新价、昨收、开高低价）。本机直连行情主站对 300308、588000 均成功返回与抓包一致的价量。曾短暂验证雪球三种时序，但用户随后明确要求独立 crate **只能使用中信证券 App 自身接口**；已从该 crate 移除全部雪球客户端和本机 stock-info API 依赖。现有 stock-info 后端的雪球 K 线政策未改、该 crate 未接入后端。

用户在 App 图表页面操作后，完整抓包新增 `0x1217` 的 58 字节请求与跨 TCP 消息分片的响应。请求的周期码位于字节 36，数量位于 44–45、倒序起始偏移位于 40–43；响应头的两字节长度用于重组完整帧，证券身份位于 16–23，记录数位于 43–44，记录从 49 起每条 36 字节，包含十进制 `YYYYMMDD` 日期、当天秒数、OHLC 四个小端浮点和原始成交量。周期码 7 为分钟线、4 为日线；服务器单页最多返回 700 条，因此五日必须用偏移分页并去重。两个市场样本在独立 crate 的真实主站验证：各 240 个当日日内点、1200 个最近五交易日分钟点、2026-11-04 至 2026-11-10 各 5 根日线，末收盘价与 `0x1214` 报价一致。K 线及五档量单位仍待与 App 页面对照。

普通/信用账户实际委托和回执仍缺协议验收：下单明确拒绝，绝不发送猜测格式的实盘委托。行情连接是原生 TCP 二进制协议，不存在 HTTP header；已参数化市场码、代码、周期、偏移、数量和服务器。交易认证/会话结构不能从行情推断。

### 鉴权边界

- **已观察**：独立进程不提供 Cookie、HTTP header、券商账户凭据或登录步骤，直接连行情主站的 `0x1214`/`0x1217` 请求对两只证券均成功；因此这些已验证的**公共行情读取**不依赖交易登录。不能外推至资讯、账户或交易接口。
- **已观察**：交易主站是独立的 `7708` 二进制连接；已保存的完整捕获从 App 启动后才启用正文记录，缺少初次账户登录/握手。其 29 字节周期心跳除了两字节序号外均相同，业务请求有 `0x0bcd` 外层命令，但没有可确认的委托提交/状态查询样本。
- **仅静态可见**：安装包将普通/信用交易分支和资金账号、客户号等登录类型分别配置；网页到原生桥接还暴露获取 SSO 令牌的调用。这不证明原生下单使用 SSO、Cookie、JWT、固定密码、某种加密算法或可重放的裸请求。实际交易会话 ID/密钥、账户绑定及响应验证仍未知，不能对外承诺鉴权方案。
