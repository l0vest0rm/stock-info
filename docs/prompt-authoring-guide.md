# Prompt 撰写指南

本指南约束本仓库所有会发送给模型的提示词。目标是让模型只感知研究任务、已确认资料、允许的检索范围和交付契约；运行时实现、调度和存储细节必须留在代码、配置和开发文档中。本指南是给维护者看的，但提示词正文必须只写给模型。

## 1. 先确定提示词的类型

先判断任务属于哪一种，再写输出契约。不要用一套模板覆盖所有任务。

| 类型 | 模型任务 | 输出契约 |
| --- | --- | --- |
| 研究报告 | 根据已确认资料和允许的公开检索形成可读结论 | 普通聊天消息中的原始 Markdown |
| 资料发现 | 搜索并返回待核验的候选资料 | 严格 JSON，字段和顶层类型固定 |
| 信息抽取/分类 | 从给定文本或标题提取受限事实 | 严格 JSON，字段、枚举和空值规则固定 |
| 写作草稿 | 根据资料撰写文章、研究摘要或候选清单 | 普通聊天消息中的原始 Markdown |

报告型任务必须写明交付载体，而不仅是写“输出 Markdown”。推荐固定表述：

> 仅在普通聊天回复中输出原始 Markdown 正文；不要创建或使用 Canvas、可编辑文档，也不要将报告作为下载文件或附件交付。

JSON 型任务不需要这段载体约束；“仅返回严格 JSON，不要 Markdown、代码围栏或说明文字”已经是足够且更合适的契约。

## 2. 模型可见内容的边界

### 提示词不是功能使用说明

提示词正文应直接命令模型完成任务。每句话都应回答“模型需要据此做什么或遵守什么”，而不是向人解释功能如何使用。

不要在提示词中写：

- 页面、按钮、API、CLI 或调用入口如何使用；
- 报告会被保存到哪里、由谁下载、后续如何展示；
- 文件路径、输出目录、任务状态、队列、重试或人工操作步骤；
- 对维护者的背景说明、实现取舍或开发备注。

这些内容应放在 README、页面文案、API 文档或代码注释中。模型唯一需要知道的是任务、资料、限制和最终回复的形态。

模型可见提示词只应包含以下四类内容：

1. 业务目标：要研究、发现、分类或提取什么。
2. 已确认资料：公司身份、时点、价格、财务数据、文本、已收录项目和明确的研究框架。
3. 证据规则：可否搜索、可用来源、不能补造什么、未知项如何表达。
4. 输出契约：正文结构，或 JSON 的字段、枚举、单位、空值和排序规则。

下列内容不得发送给模型，除非它本身是不可替代的输出字段或输入字段含义：

- 工程、程序、系统、CLI、Worker、taskd、runner、缓存、数据库、任务、阶段、内部 ID、hash、路径、文件名、版本号、部署方式。
- “工程实时获取”“程序配置”“工程摘要”“运行信息”“证据文件”“输出文件”等描述。
- `schemaVersion`、代码版本、lineage、调度状态、调用凭据和恢复标记等内部元数据。

把这类内容留在业务代码的 `diagnostics`、持久化对象、日志和开发文档中。模型只需要知道“这是已确认资料”，不需要知道资料由什么进程、表或文件得到。

### 允许保留的技术化字段

严格 JSON 输出和结构化输入中，字段名、枚举、单位和占位符是契约的一部分，可以保留。例如 `forecastMeasurement`、`category`、`null`、`{{CONTENT}}`，以及财务资料中的期间和数值表。

判断标准不是“它像不像技术术语”，而是：删除后模型是否还能正确理解输入或生成可被调用方解析的输出。若不能，保留字段并用一句业务语言解释含义；若能，删除或改写。

## 3. 输入资料的写法

### 报告和研究

- 用“已确认资料”“已确认市场快照”“研究框架（不是公司事实）”等业务标签。
- 清楚区分：已确认事实、管理层计划、外部证据、分析判断、未知项。
- 明确哪些数值不可被搜索结果覆盖，哪些历史事实必须通过公开资料核验。
- 研究框架只用于组织因果链、情景和核验重点；不得被写成公司事实。
- 缺失值应说明“未提供”“无法核验”或“数据缺失”，不得补零、反推或以模型记忆补全。

### JSON 抽取和分类

- 把输入资料称为“给出的正文、标题、元数据或目录”，而非数据库记录、缓存或管道产物。
- 用示例 JSON 定义形状，用文字定义字段含义、来源边界、单位、期间和 `null` 规则。
- 仅保留调用方实际解析的字段；不要让模型回传调试信息、去重键、路径、来源内部编号或运行状态。

## 4. 证据与检索规则

如果任务允许 Web Search，必须说明：

- 搜索要解决的业务问题；
- 可接受的来源优先级，例如公司、监管、交易所和原始公开页面；
- 哪些给定资料是固定事实，不能被搜索结果覆盖；
- 无法核验时必须保留未知；
- 链接应放在相关结论附近，而不是堆成无上下文的附录。

不要让模型感知浏览器、CDP、任务队列、会话 URL 或工具执行步骤。它只需要执行研究，不需要理解系统如何把问题送达它。

## 5. 反例与改写

| 不推荐 | 推荐 |
| --- | --- |
| 工程实时市场快照 | 已确认的市场快照 |
| 分析框架是程序配置 | 研究框架仅用于组织因果链和情景分析，不是公司事实 |
| CLI 的数据优先分 | 资料中的数据优先分 |
| 运行信息：证据文件、输出文件 | 已确认资料；文件路径不发送给模型 |
| 点击“生成报告”后由 CLI 保存 | 根据已确认资料生成报告正文 |
| 本页面会展示下列结果 | 直接输出下列结构的报告 |
| 系统按确定性规则合并 | 已收录资料清单仅供排除重复候选 |
| 不要输出内部 ID、任务日志 | 不要输出与报告无关的过程说明 |
| deterministicFlags 是工程规则触发 | 风险提示是按已给定数值识别出的异常信号 |

## 6. 编写与审查流程

1. 找到实际发送点、模型类型和调用方解析逻辑；不要只改一个 Markdown 文件后假定它生效。
2. 写出业务目标、资料边界、证据规则和输出契约；删除实现叙述。
3. 对报告型任务补充 Markdown 聊天交付约束；对 JSON 型任务逐项保留字段和枚举契约。
4. 检查占位符仍完整、唯一且由调用方提供。删除不再有业务意义的路径或运行信息占位符时，也要确认渲染器不依赖它们。
5. 更新对应的 prompt 版本，前提是该版本确实参与缓存、去重或重新生成语义；不要为了纯文字润色而触发无必要的批量重跑。
6. 重新生成运行时代码，并运行与调用方相邻的测试。

## 7. 提交前检查清单

- [ ] 模型能否在不认识本项目技术栈的前提下完成任务？
- [ ] 每一句是否都直接约束模型的任务、资料、证据或输出，而非向人讲解功能用法？
- [ ] 输入是否只包含事实、必要的结构化字段和可解释的研究框架？
- [ ] 是否泄露了路径、任务、调度、缓存、版本或内部标识？
- [ ] Markdown 报告是否明确要求普通聊天正文，而不是 Canvas/文件交付？
- [ ] JSON 任务的字段、枚举、单位、空值、顶层类型和占位符是否保持兼容？
- [ ] Web Search 是否限定了来源、固定事实和未知项处理？
- [ ] 是否已运行 `npm run build:prompts`、相邻测试和 `git diff --check`？
- [ ] 若需要真实外部验证，是否使用一个新且已授权的任务，而不是重放可能已经提交的 provider 回合？

## 8. 本仓库的维护位置

- 模型可见源文件在 [`prompts/`](../prompts/README.md)；`src/generated/prompt-text.ts` 和 `scripts/generated/prompt-text.mjs` 均为生成文件，禁止手工编辑。
- `scripts/build-prompts.mjs` 是当前统一生成入口。
- 页面/API/CLI 到具体 prompt 的映射在 [`prompts/README.md`](../prompts/README.md)。修改时必须同时检查调用方对输出和占位符的约束。
