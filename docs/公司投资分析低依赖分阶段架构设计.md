# 公司投资分析低依赖分阶段架构设计

状态：S0.1/S0.2 路由与 S1-S12 低依赖 runner 已在本地实现；生产部署、远端 D1 migration 和真实生产证明仍未完成。

适用范围：`stock-info` 的公司经营、行业、竞争、财务质量、证券估值和持续验证研究。

阅读约定：本文中的“当前”是对仓库代码、配置、迁移和已有规范的静态核对；“S0.1/S0.2 与 S1–S12”表示低依赖协议，生产部署和远端 D1 仍需单独证明。现有 [`公司投资分析大模型分阶段调用规范.md`](./公司投资分析大模型分阶段调用规范.md) 是迁移前的当前/旧契约；旧六阶段 key、输入输出和报告组装规则不能与低依赖协议混用。

## 1. 背景、目标和非目标

### 1.1 背景

当前投资分析已经从单次长 Prompt 拆成六个模型阶段，并保留阶段终态和通用 LLM run/artifact 账本。现行 runner 的定义和波次见 [`scripts/research-operating-analysis-runner.mjs`](../scripts/research-operating-analysis-runner.mjs:28-42)：

```text
company_baseline
  → industry_validation
      → [operating_analysis || financial_analysis]
          → valuation_inputs
              → valuation_conclusion
```

每个阶段目前把共享输入、该阶段的财务快照和 `dependsOn` 指向的完整上游 output 放进 `upstreamArtifacts`，见 [`scripts/research-operating-analysis-runner.mjs`](../scripts/research-operating-analysis-runner.mjs:117-123)。这使独立研究域被不必要地串联，也使后续模型重新叙述已完成的内容。

### 1.2 目标

本设计要在不减少研究内容、证据深度、反证、风险传导、情景和估值解释的前提下：

1. 将公司事实、行业结构、供需周期、竞争同行、公司经营驱动、财务质量和市场估值事实拆为相互隔离的研究域。
2. 以 S0.1 `engineering_baseline` 和 S0.2 `local_routing_match` 作为确定性、只读的内部路由层；只有确认路由后才放行 S1–S12，研究域读取同一上下文投影和最小范围投影。
3. 让详细 Markdown 负责可读研究内容，让紧凑 manifest 负责机器间依赖和追溯；下游传字段投影和 ID，不传完整上游正文。
4. 将模型检索、模型综合、确定性估值计算和确定性报告组装分离，使每一层有单一所有者。
5. 保留可恢复的 terminal artifact、attempt/lease fencing、失败原因、阻断项和定向重跑能力。

### 1.3 非目标

- 不把 LLM cache、浏览器缓存或 `app_kv` 变成事实、预测、估值或报告主表。
- 不让生产 Cloudflare Worker 调用远端 LLM；本地调用仍受 `LLM_RUNTIME=local` 边界约束。
- 不改变股票 K 线、财务报表、基金净值或其他市场数据的既有来源政策。
- 不用更短的 Prompt、减少章节或隐藏 `partial`/`blocked` 来换取更短耗时。
- 不为旧六阶段增加 legacy adapter、旧形状双写或隐式兼容路径。
- 不在本设计内授权生产迁移、生产部署、远端 D1 清理或历史数据删除。

### 2.2 重复和不必要依赖

1. **行业边界依赖是真实的，但依赖粒度过大。** 阶段二 Prompt 明确只能在阶段一确认的产品、客户、地区和用途内检索（[`industry-validation.md`](../prompts/research/operating-analysis/industry-validation.md:3)）。低依赖协议把这道门前移到 S0.2：未确认的 `companyScope` 不得进入 S1+，人工确认必须保留注册表 ID、范围说明和审计记录。
2. **全文传递扩大了所有依赖。** runner 通过 `Object.fromEntries(dependsOn.map(...))` 传递完整 output（[`runner.mjs`](../scripts/research-operating-analysis-runner.mjs:117-123)），而不是传递字段投影和稳定 ID。
3. **阶段二把多个研究域混在一个 JSON。** `validatedIndustryProfile`、`valueChain`、`profitPool`、`supplyDemandAndCycle`、`peerSet` 和公司主张交叉验证同时属于行业结构、供需周期和竞争同行三个不同所有者（[`industry-validation.md`](../prompts/research/operating-analysis/industry-validation.md:5)）。
4. **阶段三、四是合成阶段，不应重新采集。** 阶段三再次写公司概况和行业产业链；阶段四再次解释阶段一的治理/资本事实和阶段二的压力基准。它们应接收 claim/evidence 投影，而不是完整 JSON。
5. **阶段五、六的输入过宽。** 阶段五已经负责把经营和财务判断转换成情景、估值输入、风险和监测；阶段六 Prompt 只允许解释确定性结果、反证和跟踪（[`valuation-conclusion.md`](../prompts/research/operating-analysis/valuation-conclusion.md:1-12)），却仍直接依赖阶段一至四全文。
6. **最终组装隐藏了 JSON 阶段。** 当前 assembler 只拼接阶段三、四、六（[`operating-analysis-report.mjs`](../scripts/lib/operating-analysis-report.mjs:7-23)），阶段一、二、五的内容不直接出现在报告正文，迫使阶段六复述重要证据和风险。
7. **持久化追溯尚未与 runner 依赖完全对齐。** Generic artifact 类型和写入函数支持 `upstreamArtifactIds`（[`local-job-protocol.ts`](../src/shared/local-job-protocol.ts:86-137)、[`local-job-protocol.ts`](../src/shared/local-job-protocol.ts:398-432)），但当前阶段完成路径只写 output 和 terminal metadata（[`research-operating-analysis.ts`](../src/modules/research/application/research-operating-analysis.ts:229-248)）。

### 2.3 规范冲突边界

旧规范的图仍是 A→B→C→D→E→V→F（见 [`公司投资分析大模型分阶段调用规范.md`](./公司投资分析大模型分阶段调用规范.md:82-105)），并要求阶段四读取阶段三判断（见 [`公司投资分析大模型分阶段调用规范.md`](./公司投资分析大模型分阶段调用规范.md:454-506)）；当前 Prompt 和 runner 已改为阶段三、四并行，阶段五统一交叉校验。旧规范的阶段职责、章节和证据规则仍是内容基线，但其依赖图不能与本目标图混用。

## 3. 核心设计原则

### 3.1 研究深度不减少

拆分只改变所有权、传递方式和等待关系，不删除证据、来源、反证、未知项、行业专属压力、情景、敏感性、终值依赖、风险传导或监测阈值。详细研究内容仍以 Markdown 或等价的领域正文保存。

### 3.2 研究域互斥

每个研究域有唯一内容所有者。域之间可以引用 ID，但不得复制另一域的事实、正文或结论来形成“第二个同名结论”。跨域结论只由 S8、S9 或 S11 产生。

### 3.3 S0.1/S0.2 是共同只读输入与路由门

S0.1 `engineering_baseline` 只读取本地 API/结构化材料，规范化身份、时点、来源、财务/市场快照和可审计范围字段；S0.2 `local_routing_match` 只按注册表规则匹配行业模板，不调用 LLM 或 Web Search，也不把注册表本身当成公司事实。自动匹配为 `unconfirmed`、零命中、歧义或证据不足时，S1–S12 全部保持阻断；人工选择已注册模板必须通过 API 写入不可变确认审计，随后才能生成确认路由投影。研究域读取同一 `contextVersion` 和 `inputFingerprint`。

### 3.4 详细 Markdown 与紧凑 manifest 分离

详细 Markdown 服务报告和审计阅读；manifest 只保存 `artifactId`、`claimId`、`evidenceId`、`sourceId`、`unknownId`、依赖列表、状态和计数。下游默认只接收 manifest 和按字段选择的最小 projection，需要原文时按 ID 读取，不把大段上游正文塞入 Prompt。

### 3.5 稳定 ID 优先于位置和文字

`sourceId` 标识来源版本，`evidenceId` 标识来源绑定的事实，`claimId` 标识可证伪判断，`judgmentId` 标识跨证据分析判断，`assumptionId` 标识预测假设，`riskId` 标识风险传导记录，`artifactId` 标识一次 run 中的终态产物。ID 不得用数组下标或章节位置代替；改变事实、来源版本或 Prompt 版本时生成新 artifact/version，不能静默覆盖旧记录。

### 3.6 模型综合、确定性计算和组装分离

- 检索域模型负责发现、读取、抽取和标注来源，不负责生成缺失事实。
- S8/S9/S11 模型负责有证据约束的综合、假设或解释。
- S10 只由程序执行确定性估值、反向求解、敏感性和单位/数学校验。
- S12 只做固定章节组装、状态投影和来源/证据链接，不摘要、改写或删除实质内容。

## 4. 共同输入和 artifact 契约

### 4.1 S0.1 `engineering_baseline` 与 S0.2 `local_routing_match`

S0.1 输出的只读工程基线至少包含：

```json
{
  "schemaVersion": "engineering-baseline.v1",
  "researchTaskId": "...",
  "asOf": "...",
  "company": {},
  "security": {},
  "reportingBoundary": {},
  "financialSnapshot": {},
  "marketSnapshot": {},
  "companyScope": {},
  "materials": [],
  "candidateTemplates": [],
  "sourceIds": [],
  "inputFingerprint": "..."
}
```

S0.2 读取该基线和 `research-industry-template-registry.v1`，输出 `routingState`、`industryTemplateId`、`industryKey`、候选模板、逐字段证据、`mappingReason`、`unknowns` 和稳定 lineage IDs。只有 `routingState=confirmed` 才能生成 S1+ 输入。人工确认请求必须包含已注册 `selectedTemplateId`、可选 `scopeNote` 和当前候选/基线投影；服务端写入 `research_operating_analysis_routing_confirmations`，该表只追加不更新。

`companyScope` 必须明确产品、客户、地区、用途、主要业务分部和不确定边界；不能可靠确认时保留 `unknowns`，不得由股票代码或模板名称推断公司事实。

### 4.2 终态 artifact

每个 S1–S11 阶段都写一个 terminal artifact，至少包含：

- `artifactId`、`runId`、`stepKey`、`stageVersion`、`inputFingerprint`；
- `status`：`complete`、`partial`、`blocked`、`not_applicable` 或 `failed`；
- `upstreamArtifactIds`、`sourceIds`、`evidenceIds`、`claimIds`、`unknownIds`；
- 详细 `outputMarkdown` 或严格结构化 `outputJson`；
- `blockedItems`、`errorCode`、`errorMessage`、开始/完成时间、attempt 和 lease 元数据；
- `projectionVersion`（若已投影到业务读模型）。

终态 `partial` 必须说明缺口和影响范围；它不是流式截断正文。任何中间 token 都不进入业务 projection。

### 4.3 最小字段投影

投影按所有权显式声明。例如：

```json
{
  "artifactId": "llm-artifact:...",
  "claims": ["claim:operating-driver-1"],
  "sourceIds": ["source:filing-1", "source:industry-2"],
  "unknownIds": ["unknown:customer-concentration"],
  "fieldProjection": {
    "scope": {},
    "pressureInputs": [],
    "judgments": []
  }
}
```

下游若需要详情，使用 ID 读取对应 artifact 或 source registry，不复制另一阶段的完整 Markdown。

## 5. S0–S12 目标阶段

### S0.1：`engineering_baseline`（确定性输入准备）

- **职责**：读取并规范化公司/证券映射、`asOf`、报告期边界、结构化三表、市场快照、本地材料和来源注册表；整理 `companyScope`、收集依据和候选模板。
- **禁止**：Web Search、模型判断、预测、估值、行业分类猜测、把市场价格当经营事实。
- **输入**：任务请求、证券/公司主数据、已授权结构化接口和已有来源元数据。
- **输出**：`engineering_baseline`、`inputFingerprint`、`sourceIds`、范围缺口、候选模板和数据质量状态。
- **依赖**：无模型上游；只依赖确定性本地/API 数据源。

### S0.2：`local_routing_match`（确定性路由门）

- **职责**：按受控行业模板注册表匹配主营、产品边界、下游和行业事实，输出唯一命中、零命中、歧义或证据不足原因。
- **禁止**：调用 LLM/Web Search、从股票代码或模板标签推断事实、把注册表自身当作公司证据。
- **输入**：S0.1 `engineering_baseline`、注册表版本和可审计字段证据；可选服务端人工确认投影。
- **输出**：`local_routing_match`，包含 `routingState`、模板/行业 ID、候选、字段证据、`mappingReason`、unknowns 和 lineage IDs。
- **依赖**：只依赖 S0.1；`routingState=unconfirmed` 时阻断全部 S1–S12。人工确认只接受注册表 ID，并写入不可变审计后再解锁。

### S1：`company_facts`

- **职责**：公司正式披露事实、业务边界、产品/客户/地区/用途、管理层表述、会计/治理/资本事实和未知项。
- **禁止**：行业周期结论、同行排名、公司竞争优劣、财务质量评分、估值和目标价；不得重新抄录三表数值。
- **输入**：S0.1/S0.2 已确认投影、公司法定披露/IR 来源 ID和可选范围字段。
- **输出**：详细公司事实 Markdown + `evidence/claim/source` manifest；每条事实保留主体、期间、边界、单位、来源 URL 和限制。
- **依赖**：必须先通过 S0.2 路由门；之后只读取 S0.1 基线、确认路由投影和声明的来源 ID。

### S2：`industry_structure`

- **职责**：行业和可服务市场边界、上下游价值链、利润池、议价关系、资本强度和替代路径。
- **禁止**：重新介绍公司、将公司披露当独立验证、供需周期结论、同行排名和估值。
- **输入**：S0.2 确认路由和确定性 `scopeProjection.companyScope`、独立行业来源；S1 Markdown 不进入本阶段。
- **输出**：行业结构 Markdown + 行业边界、价值链、利润池 claim manifest。
- **依赖**：只依赖已确认的 S0.1/S0.2 artifact 和确定性 `scopeProjection`；路由未确认时阻断，不用宽泛行业常识继续。

### S3：`supply_demand_cycle`

- **职责**：需求、供给、库存、价格、利用率、产能、周期位置、领先指标和行业专属压力输入。
- **禁止**：判断目标公司竞争力、替同行排位、把行业增长直接写成公司增长、估值结论。
- **输入**：S0.2 确认路由或确定性 `scopeProjection.companyScope`、独立统计/协会/上下游来源；S1 Markdown 不进入本阶段。
- **输出**：供需周期 Markdown + `pressureInput`、`leadingIndicator`、`unknown` manifest。
- **依赖**：只依赖已确认的 S0.1/S0.2 artifact 和确定性 `scopeProjection`；不读取 S1 Markdown 或 S2 正文。

### S4：`competition_peers`

- **职责**：竞争市场、直接同行、替代品、产品/地区/客户/期间/会计可比性、技术/成本/认证和侵蚀路径。
- **禁止**：展开行业利润池和周期综述、替公司做三表分析、把不可比数据排名或相除、选择估值方法。
- **输入**：S0.2 确认路由或确定性 `scopeProjection.companyScope`、同行/客户/供应商/监管来源；S1 Markdown 不进入本阶段。
- **输出**：竞争同行 Markdown + peer/comparability/barrier claim manifest。
- **依赖**：只依赖已确认的 S0.1/S0.2 artifact 和确定性 `scopeProjection`；不读取 S1 Markdown 或 S2/S3 正文。

### S5：`company_operating_drivers`

- **职责**：公司特有的量、价、成本、客户、订单、产能、产品、研发、项目、增长驱动和经营催化剂。
- **禁止**：推导行业通用结论、重做竞争排名、三表质量、情景估值或目标价。
- **输入**：S0.1 已知公司来源、S0.2 确认路由和确定性 `scopeProjection.companyScope`；不接收 S1 全文或从 S1 Markdown 解析字段。
- **输出**：公司经营驱动 Markdown + driver/claim/evidence manifest。
- **依赖**：只依赖已确认的 S0.1/S0.2 artifact 和确定性 `scopeProjection`；路由或范围未知时保留 unknown/blocked。

### S6：`financial_quality`

- **职责**：结构化三表、利润与现金转换、营运资本、资本开支、资本效率、资产负债、治理/资本配置来源和压力测试。
- **禁止**：读取其他模型的经营判断、写商业模式或竞争结论、搜索替代财务数据、生成估值。
- **输入**：S0.1 结构化财务快照、S0.2 确认路由、财务来源/附注 source IDs、行业专属指标配置；缺字段必须成为 gap。
- **输出**：财务质量 Markdown + derived observation、压力结果和财务 claim manifest。
- **依赖**：S0.1/S0.2；不依赖 S1–S5 正文。若治理事实未在 S0.1 来源包中可得，输出缺口而不是隐式等待模型事实。

### S7：`market_valuation_facts`

- **职责**：当前价格、市值、证券币种/股本、历史估值观察、可比估值事实、市场隐含变量和可用/不适用估值方法。
- **禁止**：判断公司质量、选择最终情景、创造目标价、把价格变动当基本面证据。
- **输入**：S0.1 市场快照、S0.2 确认路由、证券权利/股本来源、允许的结构化市场和可比估值来源。
- **输出**：市场估值事实 Markdown + observation/comparability/source manifest。
- **依赖**：S0.1/S0.2；不依赖公司经营域。

### S8：`operating_thesis`

- **职责**：把 S1–S5 的证据连接成可证伪的“需求 → 量价 → 收入 → 利润率 → 经营结果”因果链，记录支持、冲突、替代解释和 evidence gaps。
- **禁止**：新 Web Search、补造事实、三表质量、情景假设、估值计算、重写 S1–S5 详细正文。
- **输入**：S0.1 的 compact financial trend、S0.2 确认路由 + S1–S5 的 claim/evidence manifest 和按字段投影。
- **输出**：经营 thesis Markdown + `judgmentId`、supporting/counter evidence、key variables 和 invalidation conditions。
- **依赖**：S1–S5 的终态 manifest；S6 不作为全文依赖。

### S9：`scenario_valuation`

- **职责**：基于经营 thesis、财务质量和市场估值事实构建悲观/基准/乐观情景、估值方法、DCF/反向/敏感性请求、风险传导和监测指标。
- **禁止**：新 Web Search、回头重述 S1–S7、直接生成最终 DCF 数字、修改上游事实、给交易建议。
- **输入**：S0.1 财务/市场快照、S0.2 确认路由、S8 judgments、S6 financial observations、S7 market observations 及其 IDs。
- **输出**：严格 JSON：`assumptions`、`valuationMethodSelection`、`valuationCalculationRequest`、`reverseValuationSolveTargets`、`sensitivityRequests`、`riskRegister`、`invalidationPaths`、`monitoringIndicators`、`blockedItems`。
- **依赖**：S8、S6、S7 和已确认的 S0.1/S0.2；不直接接收 S1–S5 全文。

### S10：确定性估值计算

- **职责**：按 S9 已确认的输入执行 DCF、反向求解、敏感性、终值占比、企业价值到每股价值桥接和数学/单位校验。
- **禁止**：新增经营假设、补缺失输入、调用模型、修改 S9 JSON、输出未经计算的目标价。
- **输入**：S9 `valuationCalculationRequest`、S0.1 证券/股本/币种数据、S0.2 确认路由、版本化公式。
- **输出**：版本化 deterministic result JSON、输入回链、blocked calculation items 和 calculation trace。
- **依赖**：S9 + S0.1/S0.2；不读取任何 Markdown 正文。

### S11：`investment_conclusion`

- **职责**：解释 S10 结果、市场隐含经营要求、情景差异、反证、风险和后续监测，形成最终结论。
- **禁止**：新 Web Search、修改 S9 假设或 S10 数字、重写章节 2–8、凭文字绕过阻断。
- **输入**：S9 JSON、S10 deterministic result、对应 claim/evidence/source manifest、阶段状态和 unknowns。
- **输出**：章节 9–12 Markdown + conclusion/risk/monitoring manifest；每个重要结论回链到来源、判断或计算 ID。
- **依赖**：S9、S10 和窄 provenance manifest；不接收 S1–S8 全文。

### S12：确定性报告组装

- **职责**：按固定章节、标题和状态规则拼接 S0.1/S0.2 与 S1–S11 已拥有的正文，生成 `research_operating_analysis_runs` projection。
- **禁止**：模型调用、摘要、改写、删除实质结论、补造来源、把 partial/blocked 映射为成功。
- **输入**：所有终态 artifact 的报告正文/manifest、S0.1/S0.2 元数据、质量门状态。
- **输出**：完整 12 章 Markdown、run projection、章节/来源/状态索引和 projection fingerprint。
- **依赖**：所有需要展示的终态；组装不创造新的语义依赖。

## 6. 依赖图与执行波次

### 6.1 S0.2 自动确认路由

```text
                         ┌─ S1 company_facts ────────────┐
                         ├─ S2 industry_structure ──────┤
                         ├─ S3 supply_demand_cycle ──────┤
S0.1 engineering_baseline → S0.2 local_routing_match ─┼─ S4 competition_peers ────────┼─→ S8 operating_thesis
                         ├─ S5 company_operating_drivers ┘        │
                         ├─ S6 financial_quality ────────────────┤
                         └─ S7 market_valuation_facts ────────────┘
                                                                    ↓
                                                              S9 scenario_valuation
                                                                    ↓
                                                              S10 deterministic
                                                                    ↓
                                                              S11 conclusion
                                                                    ↓
                                                              S12 assembly
```

执行波次：

1. Wave 0：S0.1。
2. Wave 1：S0.2 本地匹配；只有 `routingState=confirmed` 才放行后续波次。
3. Wave 2：S1、S2、S3、S4、S5、S6、S7 全部并行；每个阶段只读取 S0.1/S0.2 投影。
4. Wave 3：S8。
5. Wave 4：S9。
6. Wave 5：S10。
7. Wave 6：S11。
8. Wave 7：S12。

### 6.2 S0.2 未确认或证据不足

```text
S0.1 ─→ S0.2 local_routing_match (blocked/unconfirmed)
                                          └─→ S1–S12 全部 blocked，等待人工确认
S0.1 ──────────────────────────────────────────┬─→ S2 industry_structure
                                             ├─→ S3 supply_demand_cycle
                                             ├─→ S4 competition_peers
                                             └─→ S5 company_operating_drivers
S0.1 ─→ S1 company_facts
S0.1 ─────────────────────────────────────────────→ S6 financial_quality
S0.1 ─────────────────────────────────────────────→ S7 market_valuation_facts

[S2,S3,S4,S5,S6,S7] ─→ S8 ─→ S9 ─→ S10 ─→ S11 ─→ S12
```

此模式不以 S1 产出补救 S0.2。只传 S0.1 生成的短 `scopeProjection.companyScope` 和稳定 lineage IDs；路由未确认时 S1–S12 全部保持 `blocked`。人工确认通过 API 写入审计后，新的 run 才能携带确认路由投影继续；不传 S1 全文或从 S1 Markdown 解析字段。

### 6.3 并行安全规则

- 一波中的兄弟阶段必须用 `Promise.allSettled` 等待全部终止后再传播失败。
- 下游只能在声明的上游达到允许终态后开始；`partial`/`blocked` 必须按阶段最低条件判定是否放行。
- artifact ID、attempt、lease owner 和 input fingerprint 必须在 start/complete 时一致；迟到结果拒绝写入。

## 8. 失败、恢复与定向重跑

### 8.1 阶段终态和恢复边界

1. 每个阶段在 start 时保存输入投影、Prompt、`inputFingerprint` 和依赖 artifact IDs。
2. provider 返回后完成结构、证据、单位和状态校验，再一次性写 terminal artifact。
3. Node/Worker 中断时保留已完成 artifact；只重跑没有合法终态的当前阶段及其下游。
4. 过期 lease、错误 attempt 或非 owner 的迟到写入必须拒绝；恢复由新的 attempt 接管。
5. 任务完成前，所有必需章节和 projection gate 必须通过；不能以非空 Markdown、HTTP 200 或旧报告替代终态。

### 8.2 定向重跑规则

| 变化 | 最小重跑范围 |
| --- | --- |
| S0.1 公司/证券身份、`asOf` 或 scope 变化 | S0.1→S0.2；随后全部受影响 S1–S12 |
| S0.2 注册表、自动匹配或人工确认变化 | S0.2；确认路由变化后重跑全部受影响 S1–S12 |
| 公司法定披露/业务来源变化 | S1、S5、S8、S9、S10、S11、S12；若影响行业边界则追加 S2–S4 |
| 行业统计、供需或同行来源变化 | 对应 S2/S3/S4、S8、S9、S10、S11、S12 |
| 结构化三表或财务来源变化 | S6、S8（若财务 trend 变化）、S9–S12 |
| 市场价格、股本、币种或证券权利变化 | S7、S9–S12 |
| Prompt、规则、来源授权或模型版本变化 | 以新版本任务重新执行，不混用旧 artifact |

定向重跑保留未受影响 artifact，但必须建立新的 `runId`/artifact version 和完整输入指纹；禁止在同一 projection 中混合不同 context version。

## 9. 质量门和阻断语义

### 9.1 事实域门禁（S0.1/S0.2、S1–S7）

- 主体、证券、期间、币种、单位和业务边界一致。
- 每个外部事实有 `sourceId/evidenceId`、原文 URL、发布日期和限制。
- 正式披露、管理层表述、外部证据、第三方预测、结构化数据和未知项不混类。
- 不可比、冲突、缺失和 stale 数据显式记录，不填零、不平均、不用模型记忆补齐。
- S6 的报表数值只能来自结构化财务接口；S7 的价格/股本只能来自授权市场来源。

### 9.2 综合域门禁（S8–S11）

- S8 每个判断有支持 evidence、反面 evidence、关键变量、替代解释和失效条件。
- S9 每个假设有情景、期间、单位、依据 ID、反面证据、上下界和阻断状态。
- S10 只消费 S9 输入；每个结果有公式版本、输入 trace、单位和数学校验。
- S11 不新增来源、不改 S9/S10；估值数字必须来自 S10，风险和仪表盘必须可回链。
- `partial`/`blocked` 必须展示缺口和影响范围，不能映射为完成或中性结论。

### 9.3 报告门禁（S12）

- 十二章标题和顺序完整；每章只有对应所有者的正文。
- 章节 2–8 不被 S11 重写；章节 9–12 不出现未经 S10 计算的估值数字。
- projection 记录 `runId`、context version、artifact IDs、source registry、生成时间和状态摘要。

## 11. 可观测性

每个阶段和波次至少记录：

- `taskId`、`runId`、`artifactId`、`stepKey`、`waveId`、`attempt`、`leaseOwner`；
- `contextVersion`、`inputFingerprint`、上游 artifact IDs、source/claim/evidence 数量；
- started/completed 时间、provider/model/reasoning effort、输出字符或对象大小、状态和 blocked/error 计数；
- 并行波次的 start/end/settled 事件、失败原因和下游是否放行；
- S10 公式版本、计算 trace、阻断项和输出摘要；
- S12 projection ID、章节门状态、来源链接门状态和最终报告长度。

日志只记录可诊断的元数据和错误摘要，不记录 Cookie、API key 或不必要的完整模型载荷。UI 应显示当前波次、已完成域、attempt、耗时、缺口和可恢复边界，而不是把未落库 token 显示为报告正文。

## 12. 验收标准

目标迁移完成后必须同时证明：

1. S0.1 完成后，S0.2 按本地规则产生可解释候选；只有 S0.2 `routingState=confirmed` 时，S1–S7 才可在同一 context 下并行，否则 API/UI/read model 显示阻断并等待人工确认。
2. 任一 downstream Prompt 不包含不必要的完整上游 Markdown；字段投影和 artifact IDs 可从 run/artifact 账本追溯。
3. 所有研究内容仍覆盖原有十二章、证据、反证、未知项、行业压力、三情景、确定性估值和监测阈值。
4. S8/S9/S11 不能新增来源或修改确定性结果；S10 不能产生模型未确认的经营输入。
5. 任意兄弟失败都在全波 settle 后传播；已完成 artifact 在 Node 重启、lease 过期和定向重跑中保持可复用。
6. `partial`、`blocked`、`failed`、不可比和未回链状态在 API/UI/report projection 中可见。
7. S12 生成完整十二章且没有跨所有者重复改写；每个结论都能回到 source/evidence/claim/judgment/assumption/risk 或 calculation ID。
8. 本地静态、单元/契约、真实本地任务和报告 API 证据均记录；生产部署和远端 D1 仍单独验证。
